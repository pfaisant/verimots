# Verimots backend and deployment review

Review date: 2026-09-16. Candidate: D:\_agent_work\verimots-release-20260916.

Baseline: the Mac mini live AiConglomerate ods-game.mjs and ods-define.mjs were newer than the standalone source. Their functionality and eight additional live Verimots test files were imported before fixes. The standalone serve.mjs remains its own server; the AiConglomerate host was not copied over it. This review did not change production or read/write real account/leaderboard state. Fixtures use temporary files and fake/local HTTP responses.

## Fixed and verified

- Session authentication now accepts only exact cookie names, rejects duplicate/extra token components, validates expiry/subject types, compares HMACs with timingSafeEqual, and issues independent random session IDs. Logout persists a hash-based revocation, so replaying the cleared cookie fails while another device's token remains valid. Existing unexpired signed cookies remain compatible.
- Google verification reuses its OAuth client and rejects missing/oversized token input before verification. Auth requests are rate limited; HttpOnly/SameSite cookies remain intact. The 20 KB auth body allowance avoids rejecting longer genuine Google tokens.
- Cross-origin mutations are rejected. The guard compares the public Host header because the production embedding server constructs request URLs using http://localhost. Native requests without Origin remain supported.
- Rate-limit maps have a hard key limit and expiry cleanup. Forwarded client IPs are trusted only for local reverse-proxy connections, or explicit ODS9_TRUST_PROXY=1. Ranked/history/activity writes have per-account limits; feedback and guest/auth creation retain per-IP limits.
- Request bodies must be JSON objects and have byte limits. Oversized real Node request streams are drained without destroying the socket before an error response can be sent.
- Statistics writes are atomic, serialized, reject coercion, and report failures instead of silently counting an unsaved score. Failed writes do not poison subsequent writes. Corrupt account/board/stat files fail closed rather than being overwritten as if absent. Windows transient rename sharing failures get a short bounded retry; targets are never deleted as a rename fallback.
- Initial trail salt creation is shared across concurrent requests and uses exclusive file creation. Session secret creation likewise preserves an existing secret and fails if it cannot be persisted. Trail generation is deduplicated and its cache is bounded.
- Guest-to-Google adoption adds existing guest games and lifetime totals into an existing account, instead of dropping them. Board and account locks are held in the same order for the transfer. A queued score cannot recreate an already-adopted guest board row.
- History POST/DELETE accepts an optional expected owner and returns 409 without changing data if the cookie belongs to another account. Older clients that omit the owner remain supported. Stored history points/timestamps are finite and bounded.
- Daily ranking does not fabricate a one-play daily result from an old multi-play weekly aggregate. Prototype names used as board IDs return an empty board instead of accessing inherited object properties.
- Spanish FISE activity validation disallows K/W even when a blank is available. NA remains supported. Spanish/Catalan beginner fallback racks retain all eight tiles; adult random-rack scoring rejects racks over seven instead of truncating them.
- Activity retry history refuses additional unique records after 20,000 retained entries rather than growing without a hard limit or silently forgetting idempotency keys. Existing retries still resolve before the cap check.
- Definition lookup shares duplicate in-flight requests, limits outstanding distinct requests to 16, limits each lookup to 16 upstream calls/20 seconds overall, and bounds each upstream response at 2 MiB. Existing upstream-outage distinctions are preserved. All definition tests use mocked fetch; no external definitions are requested.
- Standalone serving isolates default data/secrets in gitignored .local-state, handles /welcome/, /leaderboard, proper static methods/errors, malformed encodings, hidden files, traversal/symlink confinement, HEAD, MIME types, and no-cache revalidation. Every service-worker shell URL is served successfully. A five-file whitelist streams plaintext dictionary fallback from its corresponding .txt.gz without storing another copy.
- The sync helper now excludes hidden secrets (except public .well-known), generated outputs, backups, archives, signing keys, APKs/AABs; retains dictionary gzip and the Gradle wrapper JAR; enforces source/destination mapping and hashes; refuses overlaps and symlinks; requires an empty external backup directory; verifies every rollback copy before any replacement; serializes helper deployments with a lock; copies through exclusive random temporary files and verifies them before rename; and rechecks target hashes. It leaves the AiConglomerate server and unrelated projects alone.

## Release blockers / decisions still required

1. Ranked integrity: scoreCompetePlay still accepts caller-chosen adult racks, and repeat submissions of the same official word still award additional points. This is confirmed in the live baseline and retained for client compatibility. Per-account throttling limits abuse rate but does not make the ranking cheat-resistant. A server-issued round/rack ID, bounded lifetime, single-use submission receipt and client migration are required if the official release promises trusted competitive ranking. Activity counters also validate words/racks but cannot prove that a human found them.

2. English dictionary contract: scripts/ods-game.mjs loadLexicon('en') always loads yawl.txt.gz, while the clients default to WOW24 and may select either list. submitCompete does not send a dictionary. Some valid WOW24 plays can therefore be rejected or scored against a different candidate pool. Choose and surface a fixed ranked dictionary, or carry the dictionary through server-issued rounds and both clients. No speculative scoring/list switch was made.

3. Dictionary provenance evidence: THIRD_PARTY_NOTICES.md has YAWL, WOW24, RLA-ES and DISC sections, but no section documenting the bundled French ods9.txt.gz source and redistribution basis. Its meta.json calls it a community list and carries ODS9 edition dates; that label alone supplies no provenance. The WOW24 section names an upstream downloadable list but does not state a redistribution licence. The repo has no separate bundled licence-text files. Resolve documentation/permissions evidence before claiming all bundled lists are cleared for distribution. This is a repository evidence gap, not a conclusion that any use infringes rights.

## Remaining engineering limits

- Account and leaderboard persistence are separate JSON files. Per-file atomic writes and in-process locks prevent torn files/lost concurrent writes, but a crash/disk failure between the two commits can leave profile totals and board totals inconsistent. Multiple server processes writing the same files are unsupported. A single transactional store or recoverable commit journal is the long-term fix.
- Auth/user/leaderboard JSON grows with accounts and history. Activity append growth is capped per user, but adopting several large guest histories can combine more retained retry keys than the ordinary limit. There is no automatic retention/cleanup for dormant accounts or old boards, and whole-file rewrites/all-time board scans do not scale indefinitely.
- Some legacy handlers still return generic 400 for storage failures inside broad catches, even though standalone uncaught failures correctly become 500. End-to-end typed retry/error UX remains desirable. A lost compete response can still count twice on a retry because the ranked endpoint has no idempotency key.
- Feedback/signup is durably appended before mail forwarding. If the mail relay fails, a retry can append another record or send twice. Mail delivery has a timeout but no durable outbox/deduplication contract.
- The standalone host improvements do not automatically alter the shared AiConglomerate static host. Production serving, compression fallbacks, proxy-header forwarding, timeout policy, service restart and smoke checks remain deployment responsibilities.
- Sync applies verified files sequentially, not as a multi-file atomic release. Stop/quiesce relevant writers and restart the host after completion. A concurrent non-helper edit is detected, but can leave an already-applied prefix; the external backup's plan.json and saved files are the rollback evidence. Never blindly rerun a stale plan. A killed deployment can leave .verimots-sync.lock requiring operator inspection.
- Known-source browser traffic and Android owner checks must both be exercised after deployment. No real Google login, store upload, email delivery, live-account migration, load test or adversarial distributed-abuse test was performed.
